# Localization

Free, automatic translation. The reusable part is the package `packages/auto-l10n` (`@lok/auto-l10n`): a dependency-free runtime (`t()`, `{{vars}}`, plurals, lazy loading) plus a CLI (`auto-l10n sync | check | init | scan`) and a GitHub Action template. It is plain ESM JavaScript with a hand-written `index.d.ts` so it can be published to npm with no build step. Its README is written for other game developers.

## How the game uses it

- `artifacts/survivor-616/src/locales/en.json` is the only file a person edits. Flat dotted keys (`hub.room.runs.label`). Every other `<code>.json` is generated by `.github/workflows/auto-l10n.yml` after a push that changes `en.json` or `l10n.config.json`. Never hand-write a new string into a generated file; fix a bad translation by editing it there, and it is kept until the English changes.
- `src/lib/i18n.ts` is the bridge: `t(key)` outside React, `useT()` inside components (the hook is what redraws on a language change). `MessageKey = keyof typeof en`, so a misspelled key fails `pnpm typecheck`.
- English is bundled; other languages are lazy-loaded through `import.meta.glob` (dotfiles such as `.l10n-lock.json` are skipped by the glob and by the filename pattern).
- The choice is device-local (`survivor616.lang`) and **defaults to English**. `auto` (follow the browser) is opt-in. This was deliberate: a default of "match the browser" would give Spanish-browser players a half-translated game the moment files appear, and the project rule is that new things are additive and optional.
- The Language block in Settings returns `null` until at least one generated file exists, so it adds nothing to the screen before the first Action run.
- `.l10n-lock.json` (next to the locale files) stores a hash of the English each translation came from. It decides what is stale. Commit it.

## Things that bit or will bite

- **Google Translate cannot be reached from the Claude sandbox** (the proxy refuses the CONNECT), so the real engine has never been run there. Only the Action runner or a developer machine can do the first translation. Test everything else with `--engine pseudo --targets qps`, which writes accented, padded fake text offline; delete `qps.json` and `.l10n-lock.json` before committing (the game's `i18n.test.ts` would otherwise validate it, which is harmless, but it must never ship as a language).
- The free engine is the unofficial Google web endpoint through `@vitalets/google-translate-api`. It can be rate limited or change without notice. The runner keeps partial progress and the next run continues.
- `{{placeholders}}` and the glossary in `l10n.config.json` are masked as `ZQ<n>ZQ` tokens before translation. A result that loses one is rejected and the key stays English. Add every invented noun (character, place, mode name) to `glossary` or it will be translated.
- Plurals: `key_one` / `key_other` work through `Intl.PluralRules`; languages needing `few`/`many` fall back to `_other`.
- Both lockfiles are tracked. Adding a workspace dependency means `pnpm install` (Vercel uses `--frozen-lockfile`) and `bun install --lockfile-only`.

## Coverage and what is next

- `auto-l10n scan --src artifacts/survivor-616/src` estimated about 1,078 hard-coded strings in 76 files before this work (heuristic; it cannot see strings built in `data/*.ts`). The first slice converted the title screen, `ScreenLayout`'s Back button (so "Back" is localized on every screen), Hub room labels and descriptions, the Settings header, pager and Travel fight style, and the Language picker (70 keys).
- Not covered at all: data-driven names and lore (characters, enemies, areas, lore chronicles, weapons). Plan: keys like `character.<id>.name`, with the record keeping its English as the fallback. Also not covered: text drawn on the canvas, the Remotion recap package, and right-to-left layout (`directionOf()` exists; the game only sets `<html lang>`).
- Convert screens one at a time: add keys, replace the text with `t()`, run `pnpm typecheck`.
